# 代码审查文化建设

> 从"挑错"到"协作"：打造高效的 Code Review 文化。

---

## 🎯 为什么 Code Review 重要

### 直接收益
- **发现 bug**：研究表明，Code Review 能发现 60-90% 的缺陷
- **知识共享**：团队成员了解彼此的代码，减少"单点故障"
- **代码一致性**：维护统一的代码风格和最佳实践

### 长期收益
- **团队成长**：通过 Review 学习他人的技巧和思路
- **设计质量**：在实现阶段就发现设计问题，降低重构成本
- **心理安全感**：知道有人把关，敢于尝试和犯错

## 📝 Code Review 流程设计

### 基本流程

```
1. 作者准备
   └─ 自测通过（单元测试、集成测试）
   └─ 代码符合团队规范（lint、format）
   └─ 写清楚 PR 描述：做了什么、为什么、怎么测试的

2. 提交 PR
   └─ 选择合适的 Reviewer（2-3 人）
   └─ 关联相关 Ticket/Issue

3. Reviewer 审查
   └─ 24 小时内开始 Review
   └─ 区分 "必须修改" / "建议修改" / "疑问"

4. 作者修改
   └─ 对每条评论回复（已修改 / 解释为什么不改）
   └─ 修改后 push，通知 Reviewer

5. 批准合并
   └─ 至少 1-2 个 Approval
   └─ CI 通过
   └─ 合并到主分支
```

### PR 描述模板

```markdown
## 背景
解决什么问题？关联的 Ticket 是什么？

## 改动
- 添加了 XX 功能
- 重构了 YY 模块
- 修复了 ZZ bug

## 测试
- [ ] 单元测试通过
- [ ] 集成测试通过
- [ ] 手动测试场景：...

## 截图（如适用）
（UI 改动时附截图）

## 影响面
- 影响模块：订单系统
- 数据库变更：无
- 接口变更：无
- 配置变更：无
```

## 💬 Review 评论规范

### 评论分类标签

```
🔴 [blocker] 必须修改：影响功能、安全、性能
🟡 [suggestion] 建议修改：代码质量、可读性
🟢 [question] 疑问：需要作者解释
💡 [idea] 想法：供参考，不强制
👍 [praise] 赞赏：好的实践，值得鼓励
```

### 好的评论示例

**具体且有建设性**：
- ✅ "这里用同步调用，如果下游超时会影响主流程。建议改为异步或加熔断器。"
- ❌ "这代码有问题"

**解释原因**：
- ✅ "建议用策略模式，因为后续可能会支持多种支付方式，策略模式更容易扩展。"
- ❌ "不要用 if-else"

**提问代替命令**：
- ✅ "这个魔法数字 86400 是什么意思？考虑用常量命名。"
- ❌ "魔法数字，改"

**肯定好的实践**：
- ✅ "这个错误处理很完善，覆盖了所有边界情况 👍"

## 🏗️ Review 检查清单

### 功能性
- [ ] 代码实现了需求描述的功能
- [ ] 边界情况被处理（空值、越界、异常）
- [ ] 并发安全问题（竞态条件、死锁）
- [ ] 安全性（SQL 注入、XSS、敏感信息泄露）

### 可读性
- [ ] 命名清晰（变量、函数、类名见名知意）
- [ ] 函数长度合理（< 50 行）
- [ ] 注释必要且准确（解释"为什么"而非"做什么"）
- [ ] 没有冗余代码和注释掉的代码

### 设计
- [ ] 单一职责原则
- [ ] 适当的抽象层次
- [ ] 避免过度设计
- [ ] 可测试性（依赖可注入、可 mock）

### 性能
- [ ] 时间复杂度合理
- [ ] 没有 N+1 查询
- [ ] 大数据量场景考虑分页/流式处理
- [ ] 缓存使用合理

### 测试
- [ ] 单元测试覆盖核心逻辑
- [ ] 测试用例包含正常和异常场景
- [ ] 测试独立，不依赖外部状态

## ⚠️ 常见反模式

### 反模式 1：Review 流于形式

**表现**：
- 只看格式，不看逻辑
- 秒 Approve
- "LGTM"（Looks Good To Me）但不理解代码

**解决**：
- 设定最小 Review 时间（如 10 分钟）
- Reviewer 对合并后的 bug 负部分责任
- 定期抽查 Review 质量

### 反模式 2：Review 变成"挑刺大会"

**表现**：
- 只提问题，不给建议
- 纠结于个人偏好（如缩进风格）
- 在评论中人身攻击

**解决**：
- 自动化格式检查（交给 linter）
- 区分 "团队规范" 和 "个人偏好"
- 建立心理安全感，鼓励提问

### 反模式 3：Review 阻塞过久

**表现**：
- PR 挂了一周没人 Review
- Reviewer 提了大量意见，作者改了一周
- 为了"完美"而迟迟不合并

**解决**：
- 设定 SLA：24 小时内开始 Review，48 小时内完成
- 大 PR 拆小（< 400 行变更）
- 区分 "必须修改" 和 "可以后续优化"

### 反模式 4：只有 Senior 能 Review

**表现**：
- Junior 只提交，从不 Review
- 所有 PR 都等 Senior 批准
- Senior 成为瓶颈

**解决**：
- 鼓励所有人参与 Review
- Junior Review 时关注可读性和测试
- Senior 负责架构和设计审查

## 🛠️ 工具与自动化

### 自动化检查（交给机器）

| 检查项 | 工具示例 |
|--------|----------|
| 代码格式 | Prettier, Black, gofmt |
| 静态分析 | ESLint, SonarQube, PMD |
| 测试覆盖 | Codecov, JaCoCo |
| 安全扫描 | Snyk, Dependabot |
| 性能基准 | Benchmark CI |

### 人工审查（留给人类）

- 设计合理性
- 业务逻辑正确性
- 边界情况覆盖
- 可维护性

## 📊 Review 度量与改进

### 可度量指标

| 指标 | 说明 | 健康范围 |
|------|------|----------|
| PR 平均 Review 时间 | 从提交到首次评论 | < 24h |
| PR 平均合并时间 | 从提交到合并 | < 48h |
| 每 PR 评论数 | 平均评论数量 | 5-15 |
| Review 参与率 | 团队成员参与 Review 的比例 | > 80% |
| Bug 逃逸率 | 合并后发现的 bug 数 / 总 bug 数 | < 10% |

### 改进方法
- 每月回顾 Review 数据
- 收集团队反馈（匿名问卷）
- 定期调整流程和检查清单

## 💡 我的思考

1. **Code Review 是团队文化的镜子**：如果 Review 氛围紧张、充满指责，说明团队缺乏心理安全感。如果 Review 流于形式，说明团队缺乏技术追求。

2. **小 PR 是王道**：研究表明，PR 大小与发现 bug 的数量成反比。> 400 行的 PR，Review 效果急剧下降。学会拆分任务。

3. **Review 是学习机会**：我 50% 的技术成长来自 Review 别人的代码。看到好的设计，模仿；看到坏的设计，反思自己是否也这样。

4. **国内团队的特殊挑战**：
   - 业务压力大，"没时间 Review" → 需要管理层支持，把 Review 算入工作量
   - 面子文化，不好意思指出问题 → 建立"对事不对人"的文化
   - 远程办公，缺乏面对面沟通 → 更依赖详细的 PR 描述和评论

5. **一个实用建议**：作为作者，提交 PR 前先自己 Review 一遍。很多时候自己就能发现问题，减少 Reviewer 的负担。
