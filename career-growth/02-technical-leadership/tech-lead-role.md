# Tech Lead 角色指南

> 技术负责人的职责、能力模型与常见误区。

---

## 🎯 Tech Lead 是什么

### 定义
Tech Lead（技术负责人）是**技术决策者** + **团队协调者**的混合角色。不同于纯管理的 Engineering Manager，Tech Lead 通常仍承担大量技术工作。

### 在不同公司的差异

| 公司类型 | Tech Lead 定位 | 管理职责 |
|----------|----------------|----------|
| 大厂（Google/Amazon） | 高级 IC 的职级（Staff+） | 无直接管理权，靠影响力 |
| 中型公司 | 技术 + 少量管理 | 可能带 2-5 人 |
| 创业公司 | 技术一把手 | 可能带整个技术团队 |

### Tech Lead 作为 Staff Archetype

> Tech Lead 是四种 Staff+ 原型中最常见的一种。每 8 个工程师大约需要 1 个 Tech Lead。
> —— Will Larson, *Staff Archetypes*

**关键洞察**：
- Tech Lead 日常与 Senior 工程师的工作最相似，因此是从 Senior 到 Staff 最直观的过渡
- 但「做 Tech Lead 的工作」≠「达到 Staff 级别的影响力」
- 成为 Staff 工程师不仅仅是 role——它是 **role、behavior、impact 以及组织对你这三者的认可的交集**
- 你会发现非 Staff 工程师也会表现出每种原型的行为，但 Staff 级别要求的是**持续、可验证的影响力**

## 📋 核心职责

### 1. 技术决策

**架构设计**：
- 定义系统边界和模块划分
- 选择技术栈和中间件
- 制定编码规范和最佳实践

**代码质量把控**：
- 设定 Code Review 标准
- 处理技术债务的优先级
- 推动自动化测试和 CI/CD

**示例**：
> "我们需要引入缓存层。我对比了 Redis 和 Memcached，考虑到我们需要持久化和数据结构支持，建议用 Redis Cluster。这是 ADR（架构决策记录）..."

### 2. 项目推进

**任务拆解**：
- 将大需求拆分为可并行的技术任务
- 评估工作量，识别依赖和风险
- 制定里程碑和验收标准

**进度管理**：
- 跟踪关键路径，及时暴露阻塞
- 在风险和进度间做权衡
- 向上同步状态，向下传达优先级

### 3. 团队协作

**知识分享**：
- 组织技术分享会
- 编写技术文档和 Onboarding 指南
- 推动团队内的 Code Review 文化

**跨团队协调**：
- 与产品、设计、运营对齐需求
- 协调依赖团队的时间和资源
- 处理跨系统的接口和技术契约

### 4. 人员培养

**指导初级工程师**：
- 分配适合其能力的任务
- 提供及时、具体的反馈
- 帮助制定个人成长计划

**招聘参与**：
- 定义岗位要求和面试标准
- 参与技术面试
- 评估候选人与团队的匹配度

## 🏗️ 能力模型

### 技术能力（40%）

| 能力 | 初级 TL | 高级 TL |
|------|---------|---------|
| 系统设计 | 能设计中等复杂度系统 | 能设计大型分布式系统 |
| 代码能力 | 仍写核心代码 | 写关键模块，评审架构级代码 |
| 技术广度 | 熟悉所在领域 | 跨领域知识，能评估新技术 |
| 故障处理 | 处理单系统问题 | 处理跨系统复杂故障 |

### 领导力（35%）

| 能力 | 说明 |
|------|------|
| 决策力 | 在信息不全时做出合理判断 |
| 影响力 | 不用职权推动事情发生 |
| 冲突解决 | 处理技术分歧和人员矛盾 |
| 授权能力 | 信任团队，不 micromanage |

### 业务理解（25%）

| 能力 | 说明 |
|------|------|
| 需求理解 | 理解需求背后的业务目标 |
| ROI 判断 | 评估技术投入的业务价值 |
| 优先级判断 | 在多个需求间做取舍 |
| 用户视角 | 理解最终用户的痛点 |

## ⚠️ 常见误区

### 误区 1：成为"超级 IC"

**表现**：
- 所有关键代码都自己写
- 团队成员只是执行者
- 自己成为瓶颈

**后果**：
- 团队无法成长
- 自己累死，项目仍延期
- 离职后团队瘫痪

**解决**：
- 刻意分配挑战性任务给团队成员
- 从"我做"转向"我指导"
- 培养接班人

### 误区 2：忽视沟通

**表现**：
- 只关注代码，不参加需求讨论
- 技术决策不做解释
- 状态不同步，被动救火

**后果**：
- 产品需求理解偏差
- 技术方案被挑战时无法说服
- 老板觉得"失控"

**解决**：
- 每周写技术周报
- 重大决策写 ADR 并同步
- 主动参加产品和业务会议

### 误区 3：过度追求"完美技术"

**表现**：
- 为了技术理想拒绝业务需求
- 过度设计，增加不必要的复杂度
- 忽视交付时间和成本

**后果**：
- 被业务方投诉"不配合"
- 系统过于复杂难以维护
- 错过市场窗口

**解决**：
- 理解"合适的技术"比"最好的技术"更重要
- 用 MVP 思维验证假设
- 技术债务要量化，有计划地偿还

### 误区 4：不会说"不"

**表现**：
- 所有需求都接
- 团队成员超负荷工作
- 质量下降，bug 增多

**后果**：
- 团队 burnout
- 交付质量差，口碑崩塌
- 自己成为"老好人"但无人尊重

**解决**：
- 建立需求评估流程（影响 vs 工作量）
- 向上管理，让老板理解资源限制
- 提供替代方案而非简单拒绝

## 🛠️ 实用工具箱

### 1. ADR（架构决策记录）

模板：
```markdown
# ADR-001: 引入 Redis 作为缓存层

## 状态
已接受

## 背景
订单查询接口响应时间 > 2s，影响用户体验。

## 决策
引入 Redis Cluster 作为缓存层。

## 考虑过的方案
| 方案 | 优点 | 缺点 |
|------|------|------|
| Redis | 数据结构丰富、持久化、社区活跃 | 需要运维 |
| Memcached | 简单、高性能 | 无持久化、功能单一 |
| 本地缓存 | 零依赖 | 多实例不一致 |

## 后果
- 正：查询响应时间降至 < 100ms
- 负：增加系统复杂度，需要处理缓存一致性

## 相关
- ADR-002: 缓存一致性方案
```

### 2. 技术周报模板

```markdown
## 本周进展
- 功能 A：开发完成 80%，预计下周提测
- 功能 B：已上线，无异常

## 风险与阻塞
- 依赖团队 B 的接口延迟，可能影响发布
- 已协调，对方承诺周三提供

## 下周计划
- 完成功能 A 开发和自测
- 开始性能优化专项

## 需要支持
- 申请压测环境资源
```

### 3. 1on1 谈话模板

```markdown
## 上次 Action Items 回顾
- [ ] 学习 Kafka → 进度如何？

## 本周话题
- 对当前项目的看法？
- 有什么阻碍？
- 个人成长目标？

## 本次 Action Items
- [ ] 分配一个 Kafka 相关任务
- [ ] 推荐一篇分布式系统文章
```

## 📈 成长路径

### 从 Senior 到 Tech Lead

1. **承担协调工作**：主动组织技术讨论，协调跨团队依赖
2. **培养判断力**：在 Code Review 中不仅看代码，还看设计合理性
3. **建立影响力**：通过技术分享、文档建设建立团队内的信誉
4. **理解业务**：主动参加产品会议，理解需求背后的商业逻辑

### 从 Tech Lead 到 Architect/Manager

- **Architect 方向**：更深的技术广度，跨系统的架构设计
- **Manager 方向**：更多的人员管理，团队建设和资源规划

## 💡 我的思考

1. **Tech Lead 是"翻译官"**：在技术和业务之间、团队内外之间做翻译。要把技术语言翻译成业务语言，把业务目标翻译成技术方案。

2. **最好的 Tech Lead 是"隐形"的**：团队运转顺畅，成员成长，项目按时交付——大家甚至感觉不到 TL 的存在。最差的 TL 是团队的瓶颈。

3. **技术判断力 > 技术能力**：Senior 之后，写代码的速度不再重要。重要的是在 10 个方案中选出最合适的那个。

4. **国内 Tech Lead 的特殊挑战**：
   - 业务压力大，很难保持技术深度
   - 35 岁焦虑，需要在管理和技术间做选择
   - 跨团队协作时，其他团队可能不配合

5. **一个判断标准**：如果你休假一周，团队能正常运转吗？如果不能，说明你还没有培养好团队。
