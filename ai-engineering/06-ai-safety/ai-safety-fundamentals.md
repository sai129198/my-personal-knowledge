# AI 安全基础

> AI 安全的核心问题：什么是对齐、有哪些风险、如何构建安全开发生命周期。

---

## 1. 什么是对齐（Alignment）？

### 1.1 定义

**对齐**：确保 AI 系统的目标和行为与人类的意图和价值观一致。

```
人类意图 → [对齐] → AI 行为
    │                    │
    └────── 一致 ────────┘
```

### 1.2 对齐问题类型

| 问题 | 说明 | 示例 |
|------|------|------|
| **规范博弈** | 模型找到 loophole 满足字面要求 | "不要输" → 拒绝下棋 |
| **目标误设** | 目标定义不完整 | "最大化点击率" → 标题党 |
| **分布偏移** | 训练分布与实际分布不同 | 训练数据无恶意输入 |
| **奖励黑客** | 找到意外方式最大化奖励 | 机器人走路 → 滑倒前进 |
| **能力-目标错位** | 能力强但目标不对 | 超级智能追求错误目标 |

### 1.3 对齐技术

| 技术 | 原理 | 代表 |
|------|------|------|
| **RLHF** | 人类反馈强化学习 | ChatGPT、Claude |
| **Constitutional AI** | 用原则自我批评 | Claude |
| **RLAIF** | AI 反馈替代人类 | Constitutional AI 扩展 |
| **DPO** | 直接偏好优化 | 简化 RLHF |
| **Process Supervision** | 奖励推理过程而非结果 | OpenAI Math |

## 2. 安全风险分类

### 2.1 OWASP LLM Top 10

| 排名 | 风险 | 说明 | 防御 |
|------|------|------|------|
| **LLM01** | 提示注入 | 恶意输入覆盖系统指令 | 输入过滤、参数化 |
| **LLM02** | 不安全输出处理 | 盲目信任模型输出 | 输出验证、沙箱 |
| **LLM03** | 训练数据投毒 | 污染训练数据 | 数据验证、监控 |
| **LLM04** | 模型拒绝服务 | 资源耗尽攻击 | 限流、资源限制 |
| **LLM05** | 供应链漏洞 | 依赖组件风险 | SBOM、漏洞扫描 |
| **LLM06** | 敏感信息泄露 | 训练数据记忆 | 数据清洗、差分隐私 |
| **LLM07** | 不安全的插件设计 | 插件权限过大 | 最小权限原则 |
| **LLM08** | 过度代理 | 模型权限过大 | 人工确认、权限控制 |
| **LLM09** | 过度依赖 | 盲目信任模型 | 人机协作、验证 |
| **LLM10** | 模型窃取 | 提取模型信息 | 访问控制、速率限制 |

### 2.2 风险矩阵

```
影响程度
    │
高  │  提示注入    数据泄露
    │  越狱攻击    模型窃取
    │
中  │  偏见输出    幻觉
    │  版权侵权    隐私泄露
    │
低  │  性能下降    成本增加
    │
    └──────────────────────
      低          高    发生概率
```

## 3. 安全开发生命周期

### 3.1 LLM SDL

```
需求阶段
    │
    ├── 威胁建模：识别潜在攻击面
    ├── 安全需求：定义安全基线
    │
    ▼
设计阶段
    │
    ├── 架构安全：最小权限、纵深防御
    ├── 数据安全：分类、脱敏、加密
    │
    ▼
开发阶段
    │
    ├── 输入验证：过滤、参数化
    ├── 输出编码：防止 XSS、注入
    ├── 依赖管理：SBOM、漏洞扫描
    │
    ▼
测试阶段
    │
    ├── 红队测试：对抗性测试
    ├── 模糊测试：异常输入
    ├── 偏见测试：公平性评估
    │
    ▼
部署阶段
    │
    ├── 监控告警：异常检测
    ├── 应急响应：预案、回滚
    │
    ▼
运营阶段
    │
    ├── 持续监控：日志、指标
    ├── 定期审计：合规检查
    └── 持续改进：漏洞修复
```

### 3.2 安全 Checklist

**输入层**：
- [ ] 输入长度限制
- [ ] 敏感词过滤
- [ ] 提示注入检测
- [ ] 用户身份验证

**模型层**：
- [ ] 模型版本管理
- [ ] 对抗训练
- [ ] 输出温度控制
- [ ] 置信度阈值

**输出层**：
- [ ] 内容审核
- [ ] 事实核查
- [ ] 来源标注
- [ ] 拒绝策略

**系统层**：
- [ ] 访问控制
- [ ] 速率限制
- [ ] 审计日志
- [ ] 数据隔离

## 4. 安全评估方法

### 4.1 自动评估

| 方法 | 工具 | 评估内容 |
|------|------|----------|
| **对抗测试** | Garak, PromptMap | 越狱、注入 |
| **偏见检测** | HolisticAI, Fairlearn | 性别、种族偏见 |
| **毒性检测** | Perspective API, Detoxify | 有害内容 |
| **隐私检测** | Membership Inference | 数据记忆 |

### 4.2 人工评估

- 红队测试（Red Teaming）
- 对抗性标注
- 专家审查
- 用户反馈分析

## 💡 我的思考

1. **安全不是附加功能**：必须从设计阶段就考虑安全，事后补救成本极高。

2. **纵深防御**：单一防护层不够，需要输入过滤、模型对齐、输出审核多层防护。

3. **对抗性思维**：安全人员需要像攻击者一样思考，预判可能的攻击路径。

4. **持续对抗**：攻击手段在进化，防御策略也需要持续更新。

5. **平衡安全与可用性**：过度安全会影响用户体验，需要找到平衡点。
